## Lecture Reflection
Software is a set of instructions that tell a computer how to act and perform a specific task. Software engineering adds to this by bringing key engineering principles into the process of building software. This engineering adds structure, repeatability, security, reliability and the ability to manage complexity. An example of a software I have experienced fail is our own schools website. It did not load correctly on phones when a new update that revamped the look was released. I think the developers should have looked at their end users and how they use the website and what platform they access it from. Another failure I have seen was at my own work where the camera software crashed because a small error overloaded the hard drives and it could not store the camera feed. This could have been avoided if backup storage was allocated to be only used in such instances where hard drives fail or software glitches.


## The Four Process Activities: RetailSync Case Study
Stage 1 Kickoff:
During the kickoff stage there was weak specification as there were no notes taken on the requirements which were only discussed for an hour. Development was present as design began immediately by the developer. There was no proof of validation or evolution.

Stage 2 Development:
There was weak specification again as the requirements were based of the developers assumptions. Development was weak as there was almost no coordination or any coding standards. There was no validation or evolution present here either.

Stage 3 Change of Plan:
There was once again weak specification and evolution as there was no proper documentation for the second warehouse's requirements. There was development as developers patched in the new requirements into the existing system.

Stage 4 Testing:
The specification was again weak as the original requirements were not looked back at. Validation was again weak as testing only lasted 2 days and there was no written test cases or warehouse testing. There was development as the team ran the software and fixed crashes.

Stage 5 Go live:
Development and evolution were both present as the system was deployed but the team had to fix problems and extend the project as a reaction.

In my opinion the lack of specification in the initial requirement meant that there was no real end goal for the software. This meant that the project could end up completely different to what was wanted and inevitably led to problems with bugs and bad coding practices.


## Researching a software failure
source: https://onlineethics.virginia.edu/cases/therac-25/therac-25-case-narrative

The Therac 25 radiation therapy machine caused at least 6 radiation overdoses between 1985 and 1987. When investigated it was found that the software defects were a major cause. Different parts of the software could access data without properly synchronising meaning if someone entered treatment information too quickly the machine would enter an unsafe state. The investigation also found improper testing, documentation and safety analysis wit hthe software.

The Therac 25 combined software, hardware, operator input and safety controls. This complexity made the interactions difficult to predict and test, allowing a rare timing error to result in serious consequences.
